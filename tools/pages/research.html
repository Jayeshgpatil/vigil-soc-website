Catching beacons that jitter Detection engineering

14 August 2026 · Detection Engineering · T1071.001, T1573

Command-and-control beacons used to be easy: a callback every 60 seconds, forever. Modern frameworks randomise the interval, and a naive "same destination N times an hour" rule either misses them or drowns you in software updaters.

What actually separates them

Legitimate periodic traffic and a jittered beacon both repeat. The difference is in the shape of the distribution. We score the coefficient of variation — standard deviation over mean — across the gaps between connections to the same destination. Human-driven traffic is bursty and irregular, with a coefficient well above 1. A beacon with 20% jitter sits near 0.12. An unjittered beacon sits near 0.

The trap is that software updaters, telemetry agents and NTP also sit in that low band. Interval regularity alone produces an alert queue full of your own monitoring stack. So regularity is necessary but not sufficient: it fires only alongside a second independent indicator — a destination with no reverse DNS, a process that is not a known updater, an ASN the estate has never talked to before, or a payload size distribution with almost no variance.

Result in production: across 210 estates over 90 days, the rule fired 47 times with 41 confirmed true positives. The six false positives were all the same cause — a customer's bespoke inventory agent polling on a fixed schedule from a host with no reverse DNS. We now allow-list on process signature rather than destination, because the destination changed weekly and the binary did not.

What we got wrong first

The first version keyed on destination IP. Every cloud-hosted C2 rotated addresses faster than the rule could learn them, and the allow-list we built to suppress false positives suppressed real beacons too. Keying on the (process, ASN) pair instead cut the false positive rate by roughly four-fifths and survived address rotation.

Adversary-in-the-middle phishing defeats most MFA Threat intelligence

2 August 2026 · Threat Intelligence · T1557, T1539

A reverse-proxy phishing kit does not need your password or your one-time code. It relays both to the real site in real time, and steals the session cookie the site issues afterwards. The victim signs in successfully, sees the real application, and notices nothing.

Why the second factor did not help

TOTP, push approval and SMS all authenticate a moment, not a channel. If the attacker is sitting in the middle of that moment, they inherit its result. The factor was not bypassed — it was proxied.

The controls that do break this are the ones bound to the origin. WebAuthn and passkeys sign a challenge that includes the relying party identifier, so a signature produced for login.example.com is worthless to a proxy on login-example.security-check.app. Certificate-bound sessions and device compliance checks work for the same reason: they attest to something the proxy cannot forward.

Detecting it when you cannot prevent it

Most estates cannot move every application to WebAuthn this quarter. In the meantime, the tells are on the session, not the login:

  • A session cookie first seen from one address and used minutes later from a different ASN or country.
  • Sign-in from a residential proxy range immediately followed by mailbox rule creation — the standard next step is a rule that hides the replies.
  • User agent for the authentication and for the subsequent API calls that do not match.
  • A newly registered domain, resolved from inside the estate, whose name embeds the brand of your identity provider.
Note on our own guidance: VGIL offers TOTP as a second factor, which is subject to exactly this weakness. We say so rather than implying otherwise. It is a large improvement over a password alone and a poor defence against a determined proxy — WebAuthn support is the next thing on our roadmap for this reason.

21 July 2026 · Detection Engineering · T1059

The export button is part of your attack surface

An analyst's most common action on a suspicious alert is to export it. If your export writes attacker-controlled text into a CSV without escaping, that is a code execution path from an alert straight onto the analyst's workstation.

Spreadsheets interpret a cell beginning =, +, - or @ as a formula. Alert fields are full of attacker-influenced strings: usernames, hostnames, command lines, indicator values. An attacker who can get a string into a failed-login event can get a formula into your export.

The fix is one line and belongs in the serialiser, not in each call site: prefix any cell starting with those characters — plus tab and carriage return, which parsers treat as leading whitespace before re-examining the next character — with a single apostrophe. The spreadsheet consumes it as a "treat as text" marker and shows the original string.

This is why VGIL's own CSV export defuses those prefixes, and why there is a test asserting it. A control nobody tests is a control nobody has.

9 July 2026 · Operations

De-duplication is a detection control, not a UI feature

A brute-force rule that opens a new alert per failed login produces four hundred rows for one attack. The queue is now unreadable, and the genuinely different alert that arrives during the flood is invisible.

The instinct is to fix this at the interface — collapse similar rows, add a filter. That is treating the symptom. The right place is at write time: derive a stable key from the properties that make an occurrence the same incident — rule, source, target account — and increment a counter on a match instead of inserting.

The subtlety is what belongs in that key. Include too much and every retry looks novel again. Include too little and two genuinely separate attacks merge into one, so the second one is never triaged. We key on rule, source address and targeted username: the same attacker retrying is one incident with a rising count, while the same attacker pivoting to a second account is a new one, because that pivot is exactly the escalation an analyst needs to see.
