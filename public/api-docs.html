Developers

API reference

Everything the console does, it does over this API. Pull alerts into your SIEM, drive incident workflow from a script, or export the queue for reporting — the endpoints below are the same ones the web console calls.

Authentication

Two kinds of credential

Session tokens are for people; API keys are for machines. They differ in what they can do, which is the point.

Session token

Issued by POST /api/auth/login, valid for 12 hours, and revocable from the account page. Full read and write access at the signed-in user's role. 

curl -s https://vgil.io/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"…"}'

If the account has two-factor authentication enabled, this returns {"mfaRequired":true,"challenge":"…"} instead of a token. Exchange the challenge and a code at POST /api/auth/login/mfa.

API key

Created on the account page, prefixed vgil_, and shown once. Keys are read-only — a write attempt returns 403 read_only_credential rather than failing obscurely. 

curl -s https://vgil.io/api/export/alerts \
  -H 'x-api-key: vgil_xxxxxxxxxxxxxxxx'

An unattended credential should not be able to close an incident. If you need a script to change state, use a session token belonging to a service account.

Keys are stored hashed. The plaintext appears exactly once, in the response that creates it. There is no endpoint that returns a key again — a lost key is revoked and replaced, not recovered.

Containment records
MethodPathAuthDescription
GET/containment/actionsSessionThe action catalogue: host isolation, session revocation, credential reset, account disable, edge block, process termination.
GET/containmentSessionRecent records across all incidents.
GET/containment/incident/:idSessionRecords for one incident.
POST/containmentSessionRecord a containment decision. Requires a reason, and writes to the incident timeline and audit log.
POST/containment/:id/revertSessionRecord that containment was lifted, with a reason.
These endpoints record decisions. They do not execute anything. VGIL has no agents connected to it, so an endpoint reporting "host isolated" would be asserting something it cannot know — the same reason device status is derived from telemetry rather than set by whoever asks. What an incident needs afterwards is the defensible account: what was contained, who decided, under whose authority, when, and when it was lifted.
Notifications

Alerting is opt-in. Quiet hours and digest cadence hold non-critical events for the next batch; a critical event always comes straight through, because someone who asked not to be woken still needs to hear that a domain controller is compromised. With no SMTP relay configured, notifications are still selected, rendered and logged — they appear in the delivery log marked spooled rather than being sent, so the failure mode is a visible record rather than silence.

Webhooks

Verifying a delivery

An administrator can subscribe an endpoint to incident events. Every delivery is signed, so your receiver can tell a real call from anyone who learned the URL.

Headers
x-vgil-eventEvent name, e.g. incident.opened
x-vgil-timestampUnix seconds when the call was signed
x-vgil-signaturesha256=<hex>

Events: incident.opened, incident.escalated, incident.closed, alert.critical, auth.mfa.disabled.

Checking the signature
const crypto = require('crypto');

function verify(req, secret) {
  const ts  = req.get('x-vgil-timestamp');
  const sig = req.get('x-vgil-signature');

  // Reject anything older than five minutes, or a
  // captured payload can be replayed indefinitely.
  const age = Math.abs(Date.now() / 1000 - Number(ts));
  if (!ts || age > 300) return false;

  const expected = 'sha256=' + crypto
    .createHmac('sha256', secret)
    .update(ts + '.' + req.rawBody)
    .digest('hex');

  return crypto.timingSafeEqual(
    Buffer.from(sig), Buffer.from(expected)
  );
}
Sign over the raw body. Re-serialising the parsed JSON will change key order or whitespace and the signature will not match. Capture the raw bytes before your JSON middleware runs.

Errors

Every failure returns the same shape: a stable error code to branch on, and a message written for a human. 

{
  "error": "read_only_credential",
  "message": "API keys are read-only. Use a
              session token for write operations."
}

Validation failures add a fields object keyed by input name. Internal errors carry a requestId — quote it if you report a problem.
